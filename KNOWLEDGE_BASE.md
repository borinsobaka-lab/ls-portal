# База знаний — план и архитектура

Статус: **первая версия (MVP) сделана 2026-10-24** — что именно, см. «Что
сделано» в конце; план согласован владельцем в тот же день. Код — раздел
«База знаний» в `apps/admin/CLAUDE.md`, схема — корневой `CLAUDE.md`.
Источник требований — бриф сотрудников Lady Stretch по функциям Платрума
(72 функции; рекомендации MVP / Этап 2 / бэклог / не делать). Номера
функций ниже (№) — как на листе «Сводная по функциям» брифа.

## Зачем и для кого

Портал масштабируется на сеть (100+ студий): сотрудники франшизы пишут
статьи, владельцы студий и их сотрудники читают — как вести бизнес, стандарты,
скрипты, регламенты. Сейчас — внутри текущей модели доступов админки
(владелец / администратор / тренер, «Доступы»): **владелец видит и правит
всё, остальным доступ выдаётся явно**. Отдельная система ролей франшизы
(должности, оргструктура, «с подчинёнными») — позже; схема закладывается под
неё сразу, чтобы потом не переделывать данные.

Начинаем с базы знаний; «Академия» (курсы, тесты, проверка тренером) и
адаптация — следующими модулями поверх неё.

## Решения владельца (2026-10-24)

- **Всё — на нашем сервере.** Портал потом переедет на серверы в РФ, где
  внешние сервисы блокируются: никаких платных или облачных редакторов,
  CDN, внешних шрифтов и встраиваний. Библиотеки — только открытые и
  бесплатные, собранные в наш код; во время работы страница ходит только к
  нашему API и Storage.
- **Видео — маленький лимит** на файл (50 МБ — как у Storage по умолчанию,
  менять сервер не нужно). Большое хранилище в РФ, объёмная загрузка и
  видеохостинг с CDN — отдельной задачей после переноса статей. Ссылки
  YouTube/RuTube как встроенный плеер — тоже туда (внешние сервисы).
  С 2026-10-30 лимит — 200 МБ (решение владельца;
  `db/migrations/2026-10-30_zz_kb_media_200mb.sql`, на сервере — переменная
  `FILE_SIZE_LIMIT` сервиса storage, DEPLOY.md).
  С 2026-10-27 встроенное видео с сервисов есть (решение владельца, раздел
  «Видео с сервисов» ниже): плеер грузится с сервиса, файлы — по-прежнему у нас.
- **Перенос из Платрума — вручную**: статьи заново оформляются в новом
  редакторе. Импорта нет.
- **Платрум отключается позже**, после того как у нас будет весь
  функционал; «Академия» — следующим модулем, не в первой очереди.
- **Доступы — как сейчас**: владелец выдаёт доступ каждому сотруднику в
  «Доступах». Доступ по ролям и должностям — когда будут новые роли сети.

## Что входит в первую версию (MVP)

Из брифа — все функции с рекомендацией MVP, плюс то, что почти ничего не
стоит при выбранной архитектуре (помечено ➕).

**Структура и навигация**

- Несколько баз знаний под разные цели (№1). У базы: название, короткая
  подпись для рейки, иконка, описание, порядок. Каждая база — **отдельный
  пункт в рейке слева** (переключатель «Показывать в рейке»).
- Внутри базы — дерево любой глубины из **папок и статей** (№2). Папка — это
  отдельный тип, не «статья без текста»: в отчётах папки не считаются
  статьями (боль №30), а ссылка на папку открывает её содержимое — список
  вложенного (боль №3). Верхний уровень папок — «разделы» базы (LS, LJ,
  офис/УК…).
- Перетаскивание в дереве с видимой линией «встанет сюда» / «внутрь папки»
  (№3, боль №4) + запасной вариант «Переместить…» (выбор папки в окне).
  Порядок разделов — тем же перетаскиванием, без захода в настройки (боль №1).
- Поиск по названиям и тексту статей (№8): только среди доступного,
  фильтр «во всей базе / в этой папке» (боль №5), подсветка найденного.
- Читателю не показываются пустые папки и неопубликованные статьи; у
  редактора черновики и архив — серым в дереве (боль №2, №10).
- Оглавление статьи по заголовкам — справа на широком экране (боль №2).
- Хлебные крошки, «Обновлено 24.10.2026 · Имя» в шапке статьи (боль №22).

**Редактор** — блочный «как в Notion» (№13, боли №11–12): меню «/» для
вставки блока, ручка перетаскивания блока, смена типа любого блока (в том
числе пустого), удаление из меню блока.

- Заголовки, жирный/курсив/подчёркнутый/зачёркнутый, выделение цветом
  (№14) ➕ цвет текста (боль №13 — в бэклоге брифа, но в редакторе это
  встроено), цитата, очистка стилей.
- Маркированные, нумерованные **многоуровневые** списки (№15, боль №14).
- Таблицы с выравниванием текста в ячейках (№16, боль №15).
- Картинки: загрузка, вставка из буфера, ручной размер, **несколько в ряд**
  (свой блок «галерея», №20, боль №16).
- Файлы с иконкой формата и размером, встроенный просмотр PDF (№21, боль №17).
- Видео: загрузка MP4/MOV (до 50 МБ, с 2026-10-30 — до 200 МБ) со **своим плеером** без рекламы;
  вертикальное видео не растягивается на пол-экрана, размер настраивается
  (№22, боли №18–19). YouTube/RuTube и видеохостинг — отдельной задачей.
- Аудио MP3/WAV/M4A со встроенным плеером — записи звонков (№23).
- Ссылки на сайты, **на другие статьи базы** (выбор из поиска) и на
  заголовки внутри статьи (№27).
- Вставка из Word и Google Docs с заголовками, списками, таблицами и
  стилями (№29); картинки из вставленного текста перезаливаются к нам (у
  Google Docs они по временным ссылкам и через час пропадают).
- «Сделать копию» статьи (№32; шаблоны — Этап 2).

**Публикация и версии**

- Статусы: Черновик / Опубликовано / Архив (№34). Архив вместо удаления
  (№12 закрывается им же; удаление — только у пустого черновика).
- **Автосохранение на сервер** каждые ~2 с паузы в наборе (№38): правки не
  теряются и видны с другого устройства.
- ➕ Правки опубликованной статьи копятся в черновике правок, читатели видят
  прежний текст до кнопки «Опубликовать изменения» (№35, Этап 2 в брифе):
  иначе автосохранение показывало бы читателям недописанный текст. Это
  одна колонка в таблице — дешевле, чем объяснять, почему статья «прыгает».
- ➕ Каждая публикация сохраняет снимок (кто, когда, текст) — основа истории
  версий (№36). В MVP видно «кто и когда правил», список версий с откатом —
  Этап 2 (данные уже будут копиться).

**Доступы** (№44–46, №49)

- По умолчанию **никто ничего не видит** (№44, боль №26), кроме владельца:
  он видит и правит всё (как сейчас со всеми разделами).
- В «Доступах», в карточке сотрудника — блок «Базы знаний»: по каждой
  базе «Нет доступа / Просмотр / Редактирование». Редактирование = писать и
  править статьи, папки, порядок. Создание баз, их настройки и доступы —
  только владелец («Администратор базы знаний» №45 — пока это владелец).
- Доступ к базе действует на всё её дерево (наследование, №49, боль №25):
  новая папка или статья сразу видна всем, у кого есть доступ к базе.
- Схема хранит выдачу доступа не «галочкой у сотрудника», а строкой
  «кому → к чему → уровень» (см. ниже): потом без переделки данных
  добавятся доступ по роли/должности (№47), к отдельной папке и статье
  (№48), делегирование (№50), закрытие ветки от наследования.

**Отчёт по чтению** (№55, боли №30–31)

- По каждой статье (папки не считаются): раздел, статус, автор и дата
  создания, кто и когда правил последним, у скольких сотрудников есть
  доступ, сколько открыли, % прочитавших. По нажатию — кто и когда открыл
  (первый и последний раз). Сортировка — в том числе «никто не читает» (№56
  в брифе — Этап 2, но это просто сортировка той же таблицы).
- Факт чтения пишется при открытии статьи (не чаще раза в 30 минут на
  человека и статью).

**Не делаем** (по брифу): публичный раздел без входа (№11), блок кода (№26),
обложка статьи (№30), блокировка теста после ошибки (№64).

## Архитектура

### Интерфейс

```
┌──────┬──────────────────────────┬───────────────────────────────┬─────────┐
│рейка │ меню базы (шире обычного)│ статья / папка                │оглавлен.│
│      │ [Поиск по базе……… ]      │ База › Раздел › Папка         │         │
│Дашб. │ ▾ Стандарты LS           │ Заголовок статьи              │ • Цели  │
│Клуб  │   ▸ Продажи              │ Обновлено 24.10 · Соня ●Опубл.│ • Шаги  │
│ …    │   ▾ Администратор        │                               │ • FAQ   │
│[БЗ 1]│     · Открытие смены     │ текст, картинки, видео…       │         │
│[БЗ 2]│     · Закрытие смены     │                               │         │
│──────│ ▸ Офис / УК              │                               │         │
│Доступ│ + Папка  + Статья        │                               │         │
└──────┴──────────────────────────┴───────────────────────────────┴─────────┘
```

- **Рейка** (так было в первой версии; с 1.34 — один раздел «База знаний»
  и вкладки баз в шапке, см. «Один раздел, вкладки баз и белый фон»):
  каждая база с «Показывать в рейке» — свой пункт (иконка +
  подпись до ~7 букв, как у остальных разделов) между рабочими разделами
  и нижним блоком. Внизу рейки, рядом с «Доступами» и «Клубами», — «Базы
  знаний» для владельца: список баз, создание, порядок, иконка, рейка.
  Базы без отметки «в рейке» открываются оттуда же.
- **Меню второго уровня** при входе в базу расширяется с 12rem до ~18rem и
  тянется мышью за край (ширина запоминается в браузере). В нём: поиск,
  дерево с раскрытием папок, кнопки «+ Папка / + Статья» у редактора,
  контекстное меню пункта (переименовать, переместить, копия, архив).
  На телефоне — как сейчас, выезжающим меню на всю ширину.
- **Рабочая область**: папка — заголовок, необязательное описание и список
  вложенного; статья — режим чтения, у редактора кнопка «Редактировать»
  переключает в редактор на том же месте (без отдельной страницы), сверху —
  статус, «Сохранено», «Опубликовать изменения».
- **Адреса**: `/kb/<база>` — главная базы, `/kb/<база>/<id>` — папка или
  статья (по id — ссылка не ломается при переименовании и копировании,
  «kopiya» в адресе не появляется). Ссылка на папку открывает папку.
- Ширина колонки текста — для чтения (~760px), таблицы и галереи могут
  выходить шире.

### Редактор

Выбран **BlockNote** (открытая лицензия MPL-2.0, бесплатный, на
ProseMirror/TipTap; проверено 2026-10-24: собирается в наш бандл, облака
нет; выбор эмодзи — из бандла: BlockNote отдаёт emoji-mart данные и язык
сам, эмодзи системные, без картинок — внешних запросов нет, проверено
2026-10-25): из коробки ровно
«блоки как в Notion» — меню «/», ручки перетаскивания, вложенные блоки
(многоуровневые списки), таблицы, картинки/видео/аудио/файлы с изменением
размера, вставка HTML из Word и Google Docs, есть сборка на shadcn — под
вёрстку админки. Свои блоки: галерея (картинки в ряд), PDF, ссылка на статью базы. Колонки у BlockNote — отдельный
платный/GPL-пакет — не берём; в Этапе 2 колонки — своим блоком.

Альтернатива — собрать на голом TipTap: больше контроля, но ручки блоков,
меню «/» и таблицы пришлось бы делать самим — недели работы ради того же
результата. Первый шаг разработки — короткая проверка BlockNote на наших
сценариях (вставка из реальных Word/Google Docs, таблицы и выравнивание в
ячейках, вес бандла); если
не подойдёт — TipTap.

Редактор грузится отдельным чанком только при открытии статьи (на прочие
страницы админки вес не влияет). Читатель видит ту же разметку в режиме
«только чтение».

### Данные (новые таблицы, без `studio_id` — раздел общий для сети, как «Скрипты LS»)

- `kb_bases` — базы: `title`, `rail_title`, `icon`, `description`,
  `sort_order`, `show_in_rail`, `created_by/at`.
- `kb_nodes` — единое дерево: `base_id`, `parent_id` (null — верхний
  уровень), `kind` (`folder` / `article`), `title`, `description` (у
  папки), `sort_order` (порядок среди соседей; перенос — RPC
  `kb_move_node` одной командой), `path uuid[]` (папки выше, ставит
  триггер; нужна для «искать в папке» и запрета переноса папки в саму
  себя), `status` (`draft` / `published` / `archived`), `reader_visible`
  (опубликован сам и все папки выше — так читатель не видит содержимое
  папки в черновике или архиве), `content jsonb` (опубликованный текст),
  `content_text` и `search tsvector` (русская морфология) — считает база,
  `created_by/at`, `updated_by/at`, `published_by/at` («Обновлено»).
  Адрес статьи — по id (`/kb/<база>/<статья>`): переименование и копия
  его не ломают, slug не нужен.
- `kb_drafts` — черновик правок статьи (одна строка на статью, только
  редакторам — читатель недописанное не получит даже запросом в обход
  интерфейса): `content`, `updated_by/at`. Метка `updated_at` защищает от
  затирания: сохранение со старой меткой — `kb_draft_conflict`.
- `kb_revisions` — снимок при каждой публикации: `node_id`, `content`,
  `title`, `published_by/at`.
- `kb_grants` — доступы: `base_id`, `node_id` (null — вся база; на
  будущее — ветка), `subject_type` (`user`; позже `role`, `position`,
  `studio`…), `subject_id`, `level` (`view` / `edit`). MVP пишет только
  строки «сотрудник → база → уровень» из «Доступов».
- `kb_reads` — чтение: `node_id`, `user_id`, `first_read_at`,
  `last_read_at`, `read_count`.
- Бакет **`kb-media` — закрытый**: база знаний — ноу-хау франшизы, файлы
  не должны открываться по прямой ссылке у постороннего. Путь
  `{base_id}/{node_id}/{файл}`, читать — по подписанным ссылкам (видео и
  аудио с перемоткой работают), политики Storage — по доступу к базе.

### Права в базе (RLS — граница безопасности, интерфейс только скрывает)

- Хелпер `kb_base_level(uid, base_id)` → `none` / `view` / `edit` /
  `manage`: владелец (owner хоть в одной студии) — `manage` во всех
  базах; иначе — максимум из `kb_grants` пользователя. Для политик —
  массивы баз вызывающего одним вызовом на запрос:
  `base_id = any ((select auth_kb_view_base_ids())::uuid[])`, как требует
  правило RLS-производительности (корневой CLAUDE.md, 2026-10-16).
- Читатель видит только `published` статьи и папки; редактор — всё в своих
  базах, пишет черновики `kb_drafts`, публикует, архивирует, двигает.
  `kb_bases` и `kb_grants` пишет только `manage`.
- Структурные действия — RPC (проверяют права сами): `kb_move_node`
  (запрет переноса папки внутрь себя, пересчёт `path` у ветки),
  `kb_publish`, `kb_copy_node`, `kb_mark_read`, `kb_search`, `kb_report`.
- Права в интерфейсе — `useAdminAccess()` расширяется полем `kb: Record<base,
  level>`; рейка показывает только доступные базы, guard не пускает в
  закрытую.

### Поиск

RPC `kb_search(query, base, folder)` — security invoker (RLS отсекает
недоступное): полнотекстовый поиск по-русски по названию и тексту, каждое
слово — как начало слова с морфологией («админ» найдёт «администратор»,
«кассы» — «касса»), плюс вхождение в название; результат —
статья, путь (База › Раздел › Папка) и фрагмент с подсветкой. Для тысяч
статей сети достаточно Postgres, отдельный поисковик не нужен.

### Файлы и видео — ограничение сервера

Всё (база, Storage, приложения) на одном сервере Hetzner (LAUNCH_READINESS.md).
Видео быстро съедят диск. Предложение:

- MVP: файлы в Supabase Storage, лимит бакета — 50 МБ на файл (решение
  владельца: «маленький лимит, посмотрим, как работает»), загрузка с
  полосой прогресса.
- Видео в браузере: MP4 (H.264) играет везде; MOV с iPhone (HEVC) — не в
  каждом браузере, MKV — почти нигде. Перекодирование на сервере (ffmpeg)
  нагрузит общий сервер — в MVP предупреждаем при загрузке и советуем MP4.
- Потом (отдельная задача): объёмное хранилище в РФ (S3-совместимое —
  Storage переключается на него без изменения кода) и видеохостинг с CDN и
  перекодированием, тоже на территории РФ.

## Хранилище и скорость (2026-10-25, версия 1.37)

дорогими могут стать только файлы — они лежат на диске того же сервера
(Hetzner CX32, 80 ГБ). Сделано:

- **Аналитика быстрее** (прогон: 500 сотрудников × 300 статей, год
  чтения): «Сотрудники» 16 с → 0,22 с (раньше упирались в лимит запроса
  8 с), «Обзор» 3,9 с → 0,65 с (90 дней — 0,95 с), «Статьи» 1,1 с →
  0,31 с, карточка сотрудника 0,8 с → 0,01 с. Аудитория считается одним
  запросом, а не по сотруднику.
- **Картинки сжимаются при загрузке**: больше 300 КБ — до 2000 px по
  длинной стороне в WebP (фото с телефона 5–8 МБ → 0,3–1,5 МБ). Видео,
  PDF и прочие файлы — как есть, лимит 50 МБ (с 2026-10-30 — 200 МБ).
- **«Сделать копию» копирует и файлы** — раньше копия ссылалась на файлы
  оригинала, и удаление оригинала навсегда ломало картинки копии.
- **Файлы без ссылок удаляются раз в сутки**: не нужен ни статье, ни
  черновику, ни версии, ни шаблону, ни корзине и загружен больше 7 дней
  назад (запас — на незакрытый редактор).
- **Сроки журналов**: поиск — год, чтение по дням — 400 дней (сводка
  «кто прочитал» хранится всегда).
- **«Место»** в «Управление» → «Знания» (владельцу): сколько занимают файлы
  каждой базы и шаблонов и сама база знаний в базе данных; больше 20 ГБ
  файлов — подсказка вынести их в отдельное хранилище (S3-совместимое,
  например Hetzner Object Storage).

## Оценка статей, соседние статьи, цвет базы (2026-10-25)

Решения владельца:

- **Оценка в конце статьи** — «Была ли статья полезной?» и три смайлика
  (при наведении красный, жёлтый, зелёный). Включена у всех статей,
  выключается у отдельной — «⋯» → «Настройки страницы…». Оценка своя на
  каждую опубликованную версию: поменять можно, новая версия — новая
  оценка. В аналитике — вкладка «Оценки»: сколько и как оценили (с
  прошлым периодом), по статьям, кто как оценил по хронологии. Под
  статьёй — только сама оценка, без сводок (и у редакторов).
- **«Предыдущая / Следующая»** внизу статьи — соседние статьи по порядку
  меню базы (через папки, без архива). Включено везде, выключается там же.
- **Фирменный цвет базы** — в её настройках («Управление» → «Знания» или
  карандаш на главной базы). Внутри базы им красится всё, что красилось
  цветом клуба: иконка базы в шапке, надзаголовки, точки и метки
  черновиков, оглавление. Не задан — цвет клуба.
- «Содержание» в оглавлении справа — обычным регистром, не капсом.

## Вложенные статьи (2026-10-25, версия 1.43)

Замечание владельца: вложенность была только у папок, у статьи вложенных
статей быть не могло. По брифу (№2) статья работает как раздел и показывает
вложенные статьи, вложенность многоуровневая. Теперь у статьи могут быть
вложенные статьи на любую глубину (папки по-прежнему — только в папках):
«Вложенная статья» в «⋯» статьи и строки меню, «Где создать» и
«Переместить…» предлагают и статьи, перетаскивание внутрь статьи; под
текстом статьи — список «Вложенные статьи»; статья-черновик прячет от
читателей и вложенные; в корзину статья уходит со всеми вложенными.

## Теги статей (2026-10-25, бриф №6–7, версия 1.55)

- У статьи — теги своей базы (до 10). Задаются в окне «Новая статья» и в
  режиме правки под названием: выбрать из тегов базы (поиск по набору) или
  «Создать тег «…»» — он сразу появляется в базе. Меняются без публикации.
- Читатель видит теги под названием статьи, нажатие — все статьи с тегом.
- Главная базы — блок «Теги» с числом статей; выбрал тег — вместо разделов
  список статей с ним, «Сбросить» возвращает главную. Редактор там же
  («Настроить») переименовывает и удаляет теги.
- Поиск: «касса» или «#касса» находит и статьи с этим тегом; в выпадающем
  списке сверху — найденные теги, у статей — их теги.
- Читателю видны только теги статей, которые он может открыть; теги
  уходят в корзину и возвращаются вместе со статьёй; «Сделать копию»
  копирует и теги.

## Видео с сервисов и защита картинок и видео (2026-10-27)

Решения владельца:

- **Видео с сервисов** — в меню «/» сразу за «Видео» (своим файлом):
  «Видео RuTube», «Видео Kinescope», «VK Видео», «Видео по коду iframe»
  (сначала был YouTube — владелец 2026-10-27 заменил на RuTube).
  Новый блок открывает окно «Что вставить» с подсказкой по сервису
  (`KB_EMBED_HINT` в `lib/kb/embed.ts`), поле — ссылка или код для
  вставки, «Подпись под видео». Из вставленного база не нужна — адрес
  плеера считает браузер (`parseKbEmbed` + тест): RuTube —
  `rutube.ru/video/<id>/`, `/shorts/<id>/`, закрытое
  `/video/private/<id>/?p=<ключ>` и код вставки → `rutube.ru/play/embed/<id>/`
  (ключ `p` и `t` сохраняются);
  Kinescope — `kinescope.io/<id>` или код → `kinescope.io/embed/<id>`;
  VK — код из «Поделиться» → «Экспортировать» (с `hash`, надёжнее) или
  ссылка `vkvideo.ru/video-<oid>_<id>` / `vk.com/…?z=video…` →
  `vkvideo.ru/video_ext.php`; iframe — любой https-адрес плеера, кроме
  самого портала. Ссылку известного сервиса узнаёт любой из четырёх
  пунктов. Плеер — iframe 16:9 с разрешениями из кода Kinescope
  (`allow`, полный экран), источник страницы передаётся (без него Kinescope
  с разрешёнными доменами не играет); у «iframe» — `sandbox`
  (чужой сайт не уведёт портал). Блок `embed` (`provider`, `url`, `source`
  — что вставил автор, `caption`) — `components/kb/media-blocks.tsx`; у
  редактора под плеером — сервис и «Изменить».
- **Защита содержимого — и для картинок и своего видео**: при включённой
  защите никто, и редактор тоже, не скачивает картинки (в окне просмотра
  нет «Скачать») и загруженное видео (плеер без «Скачать» и «Картинки в
  картинке» — `controlsList`, свой блок `video`), правая кнопка и
  перетаскивание у картинок и видео не работают, долгое нажатие на
  телефоне не предлагает «Сохранить». Флаг — `KbProtectContext`
  (`lib/kb/protect-context.ts`) от `KbProtectedArea`. Файлы-вложения
  («Файл», PDF) скачиваются как прежде; видео с сервисов — по настройкам
  самого сервиса.

## Упоминания и карточка сотрудника (2026-10-27)

Решения владельца:

- **Упоминание** — «@» в тексте, пункт «Упомянуть сотрудника» в меню «/»
  или кнопка «@» в панели над выделенным текстом. Список — все
  действующие люди портала с аватаркой и должностью, поиск — по имени и
  должности (то, что набрано после «@»). Сначала — у кого есть доступ к
  базе, ниже «Без доступа к этой базе» (упомянуть можно, статью они не
  откроют). Раньше в списке были только люди с доступом.
- **В тексте** — аватарка в кружке и имя (свежие: сменили фото или имя —
  меняется и в статьях). По нажатию — карточка сотрудника: фото, имя,
  должность, тип, подразделения с ролью, клубы с ролью и собственность,
  почта и телефон (скопировать одним нажатием).
- **Та же карточка** — по нажатию на автора статьи, на того, кто правил
  черновик, в «Кто прочитал», в оценках и карточке чтения аналитики, в
  списках «Академии».

## Автор статьи меняется (2026-10-28)

- Раньше «Автор» в шапке статьи — кто опубликовал последнюю версию: поправил
  опечатку и опубликовал — стал автором. Теперь редактор базы (и
  администратор баз) меняет автора карандашом у имени: список людей портала,
  как у упоминаний, сначала — с доступом к базе. Выбранный автор
  (`kb_nodes.author_id`) остаётся при следующих публикациях; «Автор — кто
  опубликовал» возвращает прежнее правило.
- Автор — только у статьи и только действующий человек портала. Смена автора
  не считается правкой статьи («кто и когда правил» не меняется).
- Выбранный автор, как прочие авторы, не входит в аудиторию отчёта по
  чтению этой статьи. Корзина возвращает автора; копия статьи — нет (копия —
  новая статья того, кто копировал).
- Схема — `db/migrations/2026-10-28_kb_article_author.sql`, окно —
  `components/kb/author-picker.tsx`.

## Порядок реализации

Каждый этап — отдельный merge в `main` (сейчас Claude мержит сам). Это
безопасно по ходу работы: пока доступ никому не выдан, базы видит только
владелец.

1. **Проверка редактора** — сделана 2026-10-24: BlockNote (см. «Редактор»).
2. **Схема и права**: миграция (таблицы, триггеры `path`/видимость/поиск,
   RLS, бакет, RPC), тесты `db/knowledge-base.test.ts` (кто что видит,
   наследование, перенос, публикация, поиск, чтение). Блок «Базы знаний» в
   «Доступах», страница «Базы знаний» владельца (создать, иконка, порядок,
   «в рейке»), базы в рейке.
3. **Навигация и чтение**: широкое меню с деревом, страница папки, статья
   в режиме чтения, крошки, оглавление, «Обновлено», поиск, отметка
   чтения.
4. **Редактор**: блоки и форматирование, загрузка картинок/файлов/видео/
   аудио, галерея, PDF, ссылки на статьи,
   вставка из Word/Docs с перезаливкой картинок, автосохранение черновика,
   публикация, архив, копия.
5. **Управление деревом**: создание из меню, перетаскивание с линией
   вставки (библиотека `@atlaskit/pragmatic-drag-and-drop` — у неё готовые
   правила «выше / ниже / внутрь» для деревьев), «Переместить…», серые
   черновики и архив.
6. **Отчёт по чтению**.
7. **Доводка**: телефон, пустые состояния, скелетоны, документация
   (CLAUDE.md — раздел базы знаний и миграции), версия админки. Задача
   агенту не нужна: лимит бакета 50 МБ — как у Storage по умолчанию.

Каждый этап проверяется: `bun run typecheck`, `lint`, `test`, миграция — на
локальном Postgres (`bash db/test/build-schema.sh`) до merge.
