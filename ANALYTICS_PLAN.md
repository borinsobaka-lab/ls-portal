# План: перенос аналитики Lady Stretch на портал

Статус: **план на согласовании** (2026-10-29). После согласования этот
документ заменит ANALYTICS.md: в нём останутся решения и описание того, что
вошло.

## 0. Коротко

Lady Stretch передала всё по своей платформе аналитики: живой код сервера
`analytics.lady-stretching.ru` на 28.10, базы, Windows-программы, служебные
скрипты и документацию. Всё изучено. Это не шесть отчётов 1С, как мы думали
(ANALYTICS.md), а целая платформа из девяти подсистем:

1. **1С** (Lady Stretch): шесть отчётов — Выручка, Продажи абонементов,
   Занятия, Воронка пробных, Нулевая номенклатура, «Мой город» партнёра. Плюс
   ежедневный ручной конвейер: 4 выгрузки из 1С → ExcelCleaner → Windows-
   обработчик (≈20 мин) → загрузка снимка на сервер. Сейчас это около часа
   работы владельца каждое утро.
2. **FitBase** (Lady Jump, 16 студий): ночная загрузка по API и сборщик
   «оснований» записей со страниц FitBase. Отчёты: Выручка, Продажи, Занятия,
   Воронка пробных, Маркетинг FitBase, «Мой город · FitBase».
3. **Маркетинг amoCRM**: отчёты «Маркетинг Lady Stretch» и «Маркетинг Lady
   Jump» — когортная воронка лидов из 50 amoCRM, обновление каждые 15 минут,
   срезы «на 1-е число».
4. **VK Ads**: 202 рекламных кабинета, ежечасный сбор, «Реестр таргета»
   (самый посещаемый отчёт), планы таргета, таргетологи. Ещё: сбор заявок
   лид-форм в Google-таблицы каждые 5 минут (своя замена Albato), источники
   «сообщений сообщества» из Google-таблиц, контроль бюджетов с
   Telegram-уведомлениями.
5. **Авито**: 14 кабинетов, реестр, планы, UTM-заявки из amoCRM.
6. **Отзывы**: оценки занятий из выгрузок 1С (522 тыс. оценок) и публичные
   ссылки, по которым партнёры оценивают сотрудников УК.
7. **Квиз-лендинги** `quiz.lady-stretching.ru` (4 города): заявки уходят в
   Google-таблицы.
8. **Ядро портала**: 92 пользователя (админы, партнёры, таргетологи,
   лид-менеджеры, сотрудники), главная с карточками, «Посещаемость», журнал,
   API для Custom GPT.
9. **VK Inbox** (`inbox.lady-stretching.ru`): рабочее место лид-менеджеров,
   мультичат 39 сообществ VK со статистикой менеджеров. Это не аналитика, а
   рабочий инструмент. **Контент-план** (автопостинг в VK) заброшен: в нём ни
   одной группы и ни одного поста.

**Что предлагаю.**
- Текущий раздел «Аналитика сети» стираем полностью: код, таблицы `an_*`,
  права и стартовые роли.
- На его месте строим раздел **«Аналитика»** с полным функционалом их
  платформы.
- Windows-обработку 1С переносим в браузер: выгрузки 1С загружаются как есть,
  без ExcelCleaner, расчёт идёт на сервере. Утренний цикл сокращается до
  выгрузки из 1С и одной загрузки.
- Фоновые сборщики (amoCRM, VK, Авито, FitBase, лид-формы) работают на сервере
  портала.
- Пользователи, права, история и настройки переносятся. Старые адреса
  (`analytics.`, `inbox.`, `quiz.`, ссылки `/feedback/…`, Callback VK, API для
  GPT) продолжают работать.
- VK Inbox — отдельным разделом портала «Диалоги», последним этапом.
- Работа идёт этапами (§12). Старый портал работает до переключения, данные
  сверяются по контрольным суммам.

Решения, которые нужны от владельца, собраны в §14.

## 1. Принципы переноса

1. **Логика — один в один.** Формулы, правила отбора, окна, округления,
   умолчания периодов и подписи — как в живом коде на 28.10 (а не как в их
   документации: где они расходятся, верен код). Найденные у них ошибки
   исправляем только с согласия владельца (список — §11). До согласования
   переносим поведение как есть.
2. **Структура и привычки — узнаваемо.** Те же отчёты, блоки, колонки, порядок,
   переключатели («Результат на 1-е число / на сегодня», «Текущее / к прошлому
   месяцу / к прошлому году», «Раскрыть все», «Показать точку 0») и цвета-сигналы
   (факт месяца, прогноз, «Итого по сети», рост и падение). Оформление — в
   дизайн-системе портала (вопрос 14.4).
3. **Граница — база.** Таблицы фактов закрыты, отчёты — RPC с проверкой прав
   (партнёр — свои города, таргетолог — свои пары «бренд + город»), как сейчас
   у `an_*_report`. Ключи интеграций доступны только серверу.
4. **Время — Москва.** Все бизнес-даты по МСК. Исключение — выручка FitBase по
   Самаре, как у них. Их местами UTC-даты — ошибка (§11).
5. **Внешние связи не рвутся.** Google-таблицы лид-форм (колонки A–V читает
   amoCRM), тот же сервисный аккаунт Google, Callback URL в 39 сообществах VK,
   публичные `/feedback/<токен>`, квиз, Action в Custom GPT, OAuth-адрес Google
   Drive.
6. **Секреты.** Не попадают в репозиторий, в интерфейсе не показываются. Токены
   переносятся перешифровкой (§10.3), а не повторным вводом 300 ключей.
7. **ПДн минимально.** Коды клиентов 1С хэшируются в браузере, как у них
   (принцип «в снимке нет клиентов»). Имена клиентов в отзывах, заявки квиза и
   ЛФ, переписка Inbox — отдельные таблицы с узким доступом.

## 4. Доступ

### 4.1 Что было

Технически две роли, `admin` и `viewer`, плюс вычисляемые типы:
- **администратор** — всё;
- **партнёр** — `viewer` с городами: «Мой город» + по галочкам «Маркетинг LS»,
  «Маркетинг LJ», «Отзывы», только свои города;
- **таргетолог** — реестр таргета и маркетинг всегда, но только по
  назначенным ему парам «бренд + город» (сопоставление по ФИО); по галочкам —
  «Реестр Авито» и отчёты FitBase на всю сеть;
- **сотрудник** — выбранные отчёты из 16 на всю сеть;
- **лид-менеджер** — только Inbox по назначенным сообществам.

### 4.2 Как будет (модель «Пользователей и ролей», ACCESS.md)

Новый блок прав **«Аналитика»** в каталоге `access_permissions`. У прав
отчётов — уровни `own` («по своим городам») и `all` («вся сеть»):

| Право | Уровни | Что открывает |
| --- | --- | --- |
| `an.onec.mycity` | own / all | 1С «Мой город» |
| `an.onec.revenue`, `an.onec.sales`, `an.onec.classes`, `an.onec.trials`, `an.onec.zero`, `an.onec.rating` | all | отчёты 1С |
| `an.fb.mycity` | own / all | «Мой город · FitBase» |
| `an.fb.revenue`, `an.fb.sales`, `an.fb.classes`, `an.fb.trials`, `an.fb.marketing` | all | отчёты FitBase, только чтение |
| `an.mkt.ls`, `an.mkt.lj` | own / all | маркетинг amoCRM |
| `an.vk.register` | own / all | реестр таргета |
| `an.avito.register` | all | реестр Авито |
| `an.reviews` | own / all | отзывы клиентов |
| `an.staff_feedback` | on | отзывы партнёров о сотрудниках |
| `an.onec.manage` | on | загрузка 1С, справочники, точка 0 |
| `an.fb.manage`, `an.crm.manage`, `an.vk.manage`, `an.avito.manage` | on | подключения, планы, таргетологи, ЛФ, СС, Telegram |
| `an.reviews.manage` | on | загрузка оценок, ссылки сотрудников |
| `an.partners.manage` | on | карточки партнёров, их города |
| `an.audit` | on | посещаемость аналитики, журнал, фоновые задачи, API для GPT |

**«Свои города» человека** = города из его карточки партнёра (`an_person_cities`),
пары «бренд + город» из назначений таргетолога (`an_vk_targetologists.user_id`)
и, по желанию владельца, города клубов, где он собственник (`studio_owners` +
связь города с клубом, §5.1). Так сохраняются обе их модели: партнёр видит
свои города, таргетолог — свои пары, без привязки по ФИО.

**Стартовые роли** (в «Пользователях и ролях»):
- «Администратор аналитики» — все права `an.*`;
- «Партнёр — аналитика» — `an.onec.mycity:own`, `an.mkt.ls:own`, `an.reviews:own`;
- «Таргетолог» — `an.vk.register:own`, `an.mkt.ls:own`, `an.mkt.lj:own`;
- «Сотрудник УК — аналитика» — набор отчётов `all` (у их 11 сотрудников наборы
  разные: при переносе группируются в роли «… (перенесено)», как в
  `access_import_legacy`);
- «Лид-менеджер» — Inbox, этап 9.

Прежние права `analytics.view/clubs/cities/manage` и роли «Аналитика сети»,
«Партнёр — аналитика», «Владелец клуба — аналитика» удаляются вместе со старым
разделом. Назначения переносятся на новые роли.

## 5. Данные

### 5.1 Справочник сети для аналитики — главное новое

У них всё связано **строками названий городов**, которые не совпадают между
системами. 1С: «Новосибирск 2», «Москва 5», «Казань Восстания + Копылова» —
это территории партнёров, а не города. В amoCRM, VK, Авито и FitBase города
пишутся вручную свободным текстом. Отсюда пустой маркетинговый отчёт у
партнёров СПб, планы без кабинетов, 7,7 % оценок без города, назначение
таргетологов по ФИО.

Вводим один справочник:
- `an_cities` — **город аналитики** = бренд + название (как «город» у них:
  территория партнёра), статус, необязательная ссылка на клубы портала;
- `an_city_aliases` — как этот город называется в каждой системе: 1С,
  amoCRM (по ответственному), VK Ads, Авито, FitBase, СС, отзывы;
- `an_studios` — студии учётных систем (1С «Структурная единица», FitBase
  club_id): город, статус «открыта / закрыта» и дата закрытия.

Все отчёты фильтруют по `an_cities.id`. Права «свои города» ссылаются на них.
Экран «Города и студии» показывает, что не сопоставлено («Город не
сопоставлен», «Студия без города»), и сопоставляет в два клика. Первичное
наполнение — из их справочника студий 1С, `city_aliases.py`, городов кабинетов
VK и Авито, ответственных amoCRM и подключений FitBase.

### 5.2 Таблицы по подсистемам (префикс `an_`)

- **1С**: загрузки `an_onec_uploads` (слот, файл, период, версия) и строки:
  - `an_onec_revenue` — студия × день: приход, расход;
  - `an_onec_sales` — строка продажи: хэш клиента, код и название
    номенклатуры, дата-время, стоимость, оплата, количество;
  - `an_onec_classes` — студия × направление × день;
  - `an_onec_visits` — записи на пробные-кандидаты: хэш клиента, членство,
    статус, дата-время.

  Справочники: `an_onec_nomenclature` (код → категория, все названия),
  `an_onec_break_even` (точка 0). Производные: `an_onec_facts` — дневные
  агрегаты, как их снимок (`items` / `facts` v1…v8). Отчёты читают их, поэтому
  открываются за миллисекунды.
- **FitBase**: `an_fb_connections` (+ правила этапов, источников, статусов,
  архивность), `an_fb_leads`, `an_fb_contracts`, `an_fb_payments`,
  `an_fb_revenue_ops`, `an_fb_events`, `an_fb_registrations`, `an_fb_kinds`
  (классификация записей и договоров с источником), `an_fb_trial_services`,
  `an_fb_service_catalog`, `an_fb_basis` (основания из HTML),
  `an_fb_web_jobs` (очередь сборщика), `an_fb_cursors`. Минимальные DTO вместо
  их 515 МБ зашифрованных кэшей.
- **amoCRM**: `an_crm_connections`, `an_crm_settings` (воронка новых лидов и
  её бренд, 6 полей), `an_crm_responsibles` (ответственный → город и партнёр),
  `an_crm_close_basis` (основания неквалификации), `an_crm_leads` (сырые
  поля: статус, ответственный, основание, источники, UTM, флаги этапов),
  `an_crm_versions`, `an_crm_lead_events`, `an_crm_snapshots` (срезы на 1-е
  число с замороженным бюджетом).
- **VK Ads**: `an_vk_accounts` (бренд, город, партнёр по `user_id`),
  `an_vk_balances` (по часам), `an_vk_campaigns`, `an_vk_stats` (только
  ненулевые строки: из 1,9 млн нужны 15 тыс.), `an_vk_forms`,

## 6. Фоновые задачи

Своя очередь в базе: `an_jobs` (расписание) и `an_job_runs` (журнал с TTL
30 дней — у них журналы росли на 60 тыс. строк в сутки). Одна задача
выполняется одним процессом — блокировка в базе. Выполнитель — сервер портала
(как пуши и сроки доступа). Переключатель `ANALYTICS_JOBS=off` позволяет
вынести задачи во второй контейнер того же образа без правок кода. Экран
«Фоновые задачи»: последний запуск, длительность, ошибки, «Запустить сейчас».

| Задача | Расписание | Что делает |
| --- | --- | --- |
| amoCRM | каждые 15 мин | инкремент сделок 50 подключений; срез на 1-е число после 00:00 МСК |
| VK Ads | каждый час | остатки, кампании, формы и связи, статистика за **3 последних дня** (у них — только вчера по UTC), контроль бюджета |
| Лид-формы VK | каждые 5 мин | новые заявки → Google-таблица кабинета (лист «Заявки», A–W); с исправленной пагинацией |
| Счётчики ЛФ | каждый час | пересчёт текущего месяца, только в сторону увеличения |
| Источники СС | каждый час | 59 пар Google-таблиц → лиды и заявки по дням |
| Авито | каждый час | структура (с пагинацией) и статистика за вчера |
| FitBase | 01:00 МСК + раз в неделю полная сверка | фазы по студиям: лиды, абонементы, оплаты, занятия, выручка, уточнение пробных |
| FitBase «основания» | каждые 5 мин | HTML-страница записей FitBase под сессией владельца, бюджет 240 с / 120 запросов |
| Telegram | после VK | новые предупреждения о бюджете партнёрам, с повторами при ошибке |
| Квиз | каждые 5 мин | доставка недоставленных заявок в Google-таблицы |
| Очистка | раз в сутки | журналы задач, ответы API, временные файлы загрузок |

Сеть сервера: VK, amoCRM, Авито, FitBase, Google — напрямую. Telegram из
России — через их Cloudflare Worker, как сейчас (адрес и секрет шлюза
переносятся).

## 7. Подсистемы

### 7.1 1С: загрузка вместо Windows-программ

**Что заменяем:** ExcelCleaner + обработчик (`desktop_app.py`,
`process.py`, справочники в Excel на ПК) + загрузку ZIP через API.

**Страница «Загрузка 1С»** (право `an.onec.manage`):
- четыре слота: «Выгрузка для НДЯ» (выручка, вся история), «Продажи» (файл
  года), «Занятия и направления» (файл года или 2018–2024), «Занятия с
  членством и клиентом» (файл месяца);
- файлы кладутся **как их сохраняет 1С**, без ExcelCleaner. Изучение
  показало, что ExcelCleaner не меняет значений, а только убирает объединения
  и группировки;
- вид определяется по шапке, слот — по периоду файла;
- разбор потоковый в браузере (Web Worker): 10-мегабайтный файл на 270 тыс.
  строк не повесит вкладку. Правила нормализации — их: «(удален)» в студии,
  протягивание даты-группы НДЯ, пропуск «Итого» и подытогов, форматы дат и
  чисел, разбор «код, номенклатура»;
- коды клиентов заменяются SHA-256 в браузере;
- до отправки — сводка: период, строки, студии, «новые студии без города»,
  «новые номенклатуры». **Новые номенклатуры классифицируются прямо здесь** —
  окно как их «Новые номенклатуры» (поиск, мультивыбор, подсказка категории по
  ключевым словам, «Классифицировано X из N»). Пока не размечено, загрузка
  отчёта не публикуется (у них так же);
- отправка пачками; новая загрузка слота **заменяет** прежнюю версию этого
  слота (у них — весь снимок). Прежняя версия хранится для отката;
- затем сервер пересчитывает производные: новые / повторные, атрибуцию
  пробных, дневные агрегаты. Это минуты вместо их 20 минут;
- журнал загрузок: «до какой даты загружено» по каждому виду.

Утренний цикл: ≈30 минут в 1С на четыре отчёта + одна загрузка. ExcelCleaner,
обработка и ZIP больше не нужны.

**Правила расчёта — один в один** (сжато; полные — в спецификации этапа):
- выручка = приход − расход; недели пн–вс с обрезкой границами; прогноз =
  факт / день окончания × дней в месяце — только для периода с 1-го числа в
  одном месяце; точка 0 — одна на город, только в строках городов и в «Мой
  город» без выбранной студии;
- продажи абонементов — оплата > 0 и категория «Абонемент». Дедупликация по
  (студия, код, клиент, дата-время, стоимость, оплата). «Новая» — самая ранняя
  дата-время клиента по всей сети за всю историю, ничьи — все новые. Без кода
  клиента — ни новая, ни повторная. «Сумма продаж» — по стоимости, оплаты — по
  оплате. Средние чеки — из сумм;
- занятия — только строки, где проведено, записано и посетило > 0; одинаковые
  ключи суммируются;
- пробное — название членства из номенклатуры категории «Пробное занятие».
  Пришёл — «прибыл», но не «не прибыл». Дедупликация (клиент, студия,
  дата-время). Покупка в окне [день пробного; +13] присваивается последнему
  пришедшему пробному, одна к одной, любая студия. Базы обеих конверсий — все
  пришедшие;
- нулевая — пустая или нулевая стоимость, кроме пробных, без дедупликации;
- сравнения — тот же диапазон −1 / −12 месяцев с обрезкой дня; карточки
  «Занятий» — к предыдущему интервалу равной длины;
- период по умолчанию — с 1-го числа по вчера (МСК).

**Отчёты** — шесть экранов по их утверждённой структуре:
- **Выручка**: 6 KPI; таблица город → студия, недели, «Итого месяца»,
  «Прогноз», «Точка 0», «Факт − точка 0», вся история месяцев; поиск, статус,
  «Раскрыть / Свернуть все», «Свернуть текущий месяц», «Показать точку 0»,
  прокрутка истории, сортировка ▼ ▲ сброс;
- **Продажи абонементов**: 6 KPI с трендом к тем же дням прошлого месяца,
  3 средних чека, 3 графика за 9 месяцев; таблица город → студия →
  номенклатура с динамикой к месяцу и году;
- **Занятия**: 6 KPI с изменением, фильтры город, студия, направления
  (мультивыбор), статус; таблица в трёх режимах;
- **Воронка пробных**: 8 KPI, таблица город → студия → направление;
- **Нулевая номенклатура**: 4 KPI, город → студия → номенклатура;
- **«Мой город»**: KPI, «Финансы» (6 месяцев, точка 0), продажи, «Что
  покупают» (Все / Новые / Продления), занятия, направления, воронка, виды
  пробных, студии города; кнопки «Оценки клиентов» и «Маркетинговый отчёт».
  Обе ведут внутрь портала, у них вторая снова вела на DataLens;
- **Рейтинг городов** — новый экран по их разовому Excel «Топ-10». Четыре
  рейтинга за месяц: покупка в день пробного, за 14 дней, продления без
  возвращённых, возвращённые (≥ 2 лет с прошлой покупки). Порог размера базы —
  вопрос 14.8.

**Перенос истории.** Сырые выгрузки за все годы (23 файла, ≈190 МБ) владелец
загружает один раз через ту же страницу. Их снимок `current.sqlite3`
загружается на экран «Сверка с прежним порталом»: отчёт сравнивает наши
дневные агрегаты с их снимком по каждому отчёту, месяцу и городу и показывает
расхождения. Перед загрузкой: выгрузки продаж за 2023 и 2024 годы у них
неполные (26 и 31 студия вместо 120–190). Их лучше переформировать в 1С
(вопрос 14.7).

**Справочники в портале** вместо Excel на ПК:
- «Города и студии» (§5.1);
- «Номенклатура»: 9 085 кодов, категории, очередь «Требует классификации»,
  массовая разметка;
- «Точка 0»: на город, по месяцам с историей значения (у них одно число «в
  месяц»).

### 7.2 FitBase

Переносится целиком: подключения 16 студий (Bearer + `club` / `domain`,
фиксированный хост, без редиректов) с правилами этапов, источников и статусов,
архивностью, выбором пробных услуг филиала. Ночная очередь, инкремент по
`updated_at` с перекрытием 300 с, адресная сверка занятий по `event_id`,
транзакционная замена данных фазы.

Отчёты по формулам их кода: маркетинг (когорта лидов
по этапу, бюджет VK ×1,22), продажи (договоры с ценой > 0, деньги по дате
платежа, «Не распределено», средний чек по оплаченным договорам), посещаемость
(записи, а не люди; записались — статусы 0, 1, 3, 4, 5), выручка (Самара, по
вчера, прогноз, «*» при неполноте), воронка пробных (подтверждённая выборка,
зрелые окна, «Записи без услуги» + CSV), «Мой город · FitBase».

**Сборщик оснований** (HTML `/client-schedule/index`) — задача портала с их
белым списком путей и контролем пагинации. Вход в FitBase защищён CAPTCHA,
поэтому сессию по-прежнему получает владелец. Вместо их Python-помощника и
SSH — страница «Подключить сессию FitBase»: владелец входит в FitBase в
браузере и передаёт cookies (вопрос 14.10).

Исправить (с согласия): «… после пробного» ошибочно считаются пробными;
«Студий с ошибками: 16» каждую ночь — у уточнения пробных будет свой статус
качества; зависание «Выполняется» (контроль живости); полная сверка раз в
неделю; точка 0 Lady Jump берётся из целей Lady Stretch.

### 7.3 Маркетинг amoCRM (Lady Stretch, Lady Jump)

- Подключения (адрес, долгоживущий токен), загрузка воронок, полей и
  ответственных, правила (воронка новых лидов и её бренд, авто-источник,
  источник партнёра, «Запись», «Визит», «Продажа», «Основание для закрытия»),
  ответственный → город и партнёр, отметки неквалификации, «Полная сверка» —
  фоновой задачей с прогрессом (у них — синхронно в запросе).
- Синхронизация: только GET `/api/v4/leads` по `updated_at`, перекрытие
  15 мин, старт аналитики 01.09.2026, только воронка новых лидов при первом
  появлении, флаги — непустой текст, нормализация «купил ⇒ пришёл ⇒
  записался», `status_id = 143` + отмеченное основание = неквалифицированный.
- Отчёт: месяц когорты по МСК, блоки «город × партнёр», каналы, 14 колонок,
  5 KPI, подсказка «?» с основаниями, «Город не сопоставлен» последним, режимы
  «на сегодня» / «на 1-е число». Срез фиксируется один раз и не меняется.
  Бюджеты VK: ЛФ = расход ЛФ × 1,22, СС = (весь VK − ЛФ) × 1,22, замораживаются
  в срезе.
- Улучшение без смены цифр: квалификация, город и партнёр считаются в
  запросе по текущим справочникам. Смена соответствий действует сразу, без
  «полной сверки». Сырые поля храним.
- Перенести обязательно: срезы и их бюджеты, историю версий, события этапов —
  из amoCRM их не восстановить.

### 7.4 VK Ads и «Реестр таргета»

- Кабинеты (202): токен, бренд, город, партнёр (по `user_id`, не по ФИО),
  «Ключ и загрузка» за период — фоновой задачей.
- «Расходы по кабинетам»: дата, 4 KPI, таблица с ЛФ и СС.
- **Реестр таргета** — главный экран:
  - фильтры: период, направление, таргетолог; три плашки «Лид-формы»,
    «Сообщения сообщества», «Итого»;
  - группы по таргетологам, «Не назначен» внизу; 9 колонок, раскрытие ЛФ /
    СС / общие;
  - **динамический план периода**: остаток месячного плана после полученных
    заявок, на оставшиеся дни, вверх. Плановый бюджет = ⌈план⌉ × CPL;
  - **дни без бюджета** по правилу 12.10 (утренний и вечерний остатки
    относительно дневного плана, 50 % расхода). Их зашитое исключение
    «Владимир, 07.10» становится записью в таблице исключений;
  - квалификация VK из amoCRM; статусы и цвета.
- Планы таргета: ручной ввод, импорт Excel «Город / Заявки / Стоимость заявки»
  (один месяц или все листы), история правок, удаление.
- Таргетологи: бренд + город → пользователь.
- Источники СС: две Google-таблицы на пару — лист «Сбор лидов», дата в
  колонке C; лист «Номера», дата в D — с их разбором дат.
- **Лид-формы**: 5-минутный сбор в те же 202 таблицы тем же форматом A–W
  (A–V не двигать: их читает amoCRM), создание таблиц в папке Drive, бэкфилл
  счётчиков без уменьшения.
- Контроль бюджетов: прогноз по 7 дням, уровни ≤ 3 / ≤ 1 / 0 дней,
  пополнение до 7 дней; Telegram-бот через их шлюз; привязка чатов партнёров.
  Сейчас привязок 0 — функция готова, но не используется.
- Не переносим их ошибки: лиды VK отдаёт не больше 50 за запрос (у них
  читается только первая страница), список форм не больше 20 (у 13 кабинетов
  старые формы теряют связи, расход уходит из ЛФ в СС), даты по UTC, Telegram
  без повторов, удаление кабинета с заявками падает.

### 7.5 Авито

Кабинеты (`client_credentials`), структура «кампания → группа → креатив»
**с пагинацией**, статистика за вчера, история блоками по 100 дней.
Реестр: город → кабинет → РК → группы и креативы, заявки из amoCRM по ключу
«бренд + город + utm_medium + utm_campaign + utm_content» (только однозначные),
«не распределены», планы заявок и CPL с пропорцией по дням, плашки «Нужно N /
+N сверх», «В норме / Выше цели». Расход — без ×1,22, как у них. Исправить
(с согласия): `utm_source=avito-ads` с дефисом не распознаётся как Авито — так
размечены 198 из 481 креатива.

### 7.6 Отзывы

- **Отзывы клиентов**: загрузка выгрузки оценок 1С (.xls / .xlsx, 9 колонок,
  дедупликация по хэшу строки, «Добавлено N, повторы не добавлены M»);
  витрина: город и период по дате оценки, средняя, распределение 5…1,
  «≤ 3», тренеры (худшие сверху), комментарии с пагинацией. Город берётся по
  справочнику студий (§5.1). У них 7,7 % оценок без города никто не видел.
  Права — свои города или вся сеть.
- **Отзывы партнёров о сотрудниках УК**: постоянная ссылка на человека портала,
  публичная форма `/feedback/<токен>` (город, имя партнёра, две оценки 1–5,
  рекомендация обязательна при ≤ 4, ловушка для ботов + ограничение частоты),
  статистика по сотрудникам и комментарии. **Токены 20 ссылок сохраняются**:
  ссылки уже разосланы партнёрам.
- Исправить (с согласия): удаление загрузки у них не удаляет строки (20 тыс.
  «осиротевших» оценок до сих пор в отчётах); сотрудник с правом видит пустую
  страницу; колонка «NPS» — это среднее из 5; старые ответы в шкале 1–10
  входят в средние нулями.

### 7.7 Квиз

Публичный приём заявок `POST /api/leads` для `quiz.lady-stretching.ru` с
проверкой Origin, хранение заявок, доставка в Google-таблицу города
**очередью с повторами** (у них при сбое Google заявка «терялась» до следующей).
Лендинги (4 города): переносим статику на сервер портала и ведём города
лендингов (адрес, цена пробного, оператор ПДн, таблица) в настройках вместо
`config.js` в коде. Вопрос 14.9: продолжать ли квиз.

### 7.8 Ядро: главная, «Посещаемость», журнал, API для GPT

- «Посещаемость аналитики»: визиты, активное время (пульс видимой вкладки,
  как у них: 15 с, интервал ≤ 45 с, простой 180 с), просмотры, какие отчёты,
  «не заходили». У них с 14.10 не учитываются отчёты 1С — у нас учитываются
  все экраны.
- Карточка партнёра: ИП, ИНН, телефон, Telegram, MAX; по городам — цена
  пробного и направления (переносим, заполнено мало).
- **API для Custom GPT**: `/openapi.json`, `/api/v1/catalog`,
  `/api/v1/dashboards/{revenue|subscriptions|activities|trial_funnel}` — те же
  адреса и формат, но **живые данные** (у них — замороженные HTML от 13.10).
  Хэш ключа переносится. Если `analytics.lady-stretching.ru` указывает на
  портал, GPT продолжает работать без перенастройки.

### 7.9 VK Inbox → раздел «Диалоги» (этап 9)

Отдельный раздел рейки, не аналитика. Переносится целиком:
- очередь с поиском и фильтром групп, «Непрочитанные» с базовой линией;
- ответ: текст, до 4 фото, эмодзи, личные и общие шаблоны;
- карточка клиента;
- статистика лид-менеджеров по их формулам: лиды по дате первого сообщения из
  VK, уникальные телефоны, скорость ответа (медиана, p90), CSV;
- назначение групп лид-менеджерам;
- приём Callback VK: публичный маршрут, проверка sha256 секрета —
  перенастраивать 39 групп не нужно, если сохранить адрес;
- живое обновление через Supabase Realtime вместо опроса раз в 8 секунд;
- фоновая сверка дат первых сообщений.

Перенос данных: ≈330 тыс. сообщений, диалоги, прочтения, шаблоны, даты первых
сообщений. Пользователи сопоставляются по почте.

### 7.10 Контент-план и ExcelCleaner

- **Контент-план**: данных нет, публикация картинок упёрлась в права VK.
  Предлагаю не переносить сейчас, оставить в бэклоге (вопрос 14.3).
- **ExcelCleaner** для загрузки 1С не нужен (§7.1). Если им чистят и другие
  выгрузки, в «Данные и настройки» добавляется небольшой инструмент «Очистка
  Excel»: файл → плоский .xlsx, всё в браузере (вопрос 14.3).

## 8. Как это ложится на код портала

- Код раздела:
  - `apps/admin/src/routes/_authenticated/analytics/**`;
  - `components/analytics/**` — по подпапкам `onec/`, `fitbase/`,
    `marketing/`, `vk/`, `avito/`, `reviews/`, `admin/`;

- Серверная часть: `lib/analytics/jobs/*.server.ts` (сборщики и клиенты API),
  `lib/analytics/secrets.server.ts` (AES-256-GCM, ключ
  `ANALYTICS_SECRETS_KEY` в Coolify).
- Публичные маршруты в `routes/api/`: `/api/leads` (квиз), `/feedback/$token`,
  `/api/vk-inbox/callback/$id`, `/api/v1/*`, `/openapi.json`, OAuth-возвраты
  Google.
- Схема: миграции `db/migrations/2026-…_analytics_*.sql` по этапам, тесты базы
  `db/analytics*.test.ts` — права (партнёр не видит чужой город, таргетолог —
  чужую пару), пересчёты, замена слота.
- Отчёты — RPC `an_*_report` (security definer, проверка прав, агрегаты jsonb,
  без лимита PostgREST). Тяжёлое — дневные агрегаты, их пересчитывает сервер
  после загрузки или сбора.
- Главная портала: людям только с аналитикой (партнёрам) рейка открывается
  на «Аналитике», базы знаний и Академия остаются.

## 10. Перенос данных и переключение

### 10.1 Пакет переноса

Скрипт выгрузки запускается на их сервере, только чтение — как их «.bat» с
SSH. Он собирает компактный пакет: SQLite с нужными таблицами. Без мусора: их
журнал `sync_runs` весит 438 МБ, кэши FitBase — 515 МБ, сырые ответы VK —
тоже лишние.

В пакет входят:
- ядро: пользователи, выдачи, города партнёров, карточки, журнал,
  посещаемость, хэши ключей API;
- 1С: справочники студий, номенклатуры (рабочий экземпляр, 9 085), точки 0 и
  снимок для сверки;
- amoCRM: всё, кроме сырого кэша метаданных;
- Авито;
- VK Ads: без `sync_runs` и нулевой статистики;
- FitBase: настройки, факты, основания и очередь сборщика;
- отзывы и ссылки;
- квиз;
- Inbox — отдельным дампом на этапе 9.

Владелец загружает пакет на странице «Перенос» (только суперадминистратор).
Импорт идемпотентный: повторный запуск перед переключением докатывает разницу.

### 10.2 Сверка

Для каждого модуля — экран «Сверка с прежним порталом»:
- 1С — по их снимку;
- amoCRM — контрольные KPI месяцев в обоих режимах;
- реестр таргета — за период;
- Авито, FitBase, отзывы — итоги.

Расхождения разбираются до переключения. Контрольные суммы есть в материалах.
В репозиторий они не попадают: в них выручка сети.

### 10.3 Ключи интеграций

Около 300 ключей: 202 токена VK, 50 amoCRM, 14 пар Авито, 16 FitBase,
39 токенов сообществ Inbox, Telegram, Google Drive. Все зашифрованы их ключом
`VK_ADS_CREDENTIAL_KEY` по их схеме (XOR + HMAC-SHA256). На время импорта
владелец задаёт этот ключ переменной в Coolify. Сервер расшифровывает их
алгоритмом, шифрует нашим ключом, после чего переменная удаляется. Заново
вводятся только:
- JSON сервисного аккаунта Google — тот же аккаунт, иначе придётся заново
  расшаривать 202 + 118 таблиц;
- OAuth-клиент Drive + повторный вход;
- сессия FitBase (CAPTCHA).

### 10.4 Как переключаемся

Сборщики, которые только читают (VK статистика, amoCRM, Авито, FitBase API),
работают **параллельно со старым порталом** с первого дня этапа: сверка идёт
на живых данных. Сборщики с внешними действиями включаются в момент
переключения, предварительно старые таймеры останавливаются, а последние ID
переносятся:
- лид-формы → Google-таблицы;
- Telegram;
- квиз → таблицы;
- ответы и Callback Inbox.

Переключение пользователей — волнами (вопрос 14.1):
1. **Волна 1** — 1С, «Мой город», отзывы, пользователи и партнёры, посещаемость.
2. **Волна 2** — маркетинг: amoCRM, VK Ads, Авито, квиз; FitBase.
3. **Волна 3** — Диалоги VK.

После последней волны старый сервер 2–4 недели в режиме «только чтение», затем
выключается. Архив остаётся у владельца.

### 10.5 Адреса

DNS-записи `analytics`, `inbox`, `quiz` в зоне `lady-stretching.ru`
переводятся на сервер портала (Coolify: дополнительные домены приложения).
Сервер портала по хосту и пути отвечает так:
- `analytics.…/1c?report=revenue&start=…` → `portal.…/analytics/revenue?…`
  (параметры сохраняются), так же для всех старых путей;
- `analytics.…/feedback/<токен>` — форма отзыва;
- `analytics.…/api/v1/*`, `/openapi.json` — API для GPT;
- `inbox.…/api/vk-inbox/callback/<id>` — приём VK (те же внутренние id групп);
- `inbox.…/admin/vk-inbox` → раздел «Диалоги»;
- `quiz.…/<город>/` и `quiz.…/api/leads` — квиз.

OAuth-адрес Google Drive добавляется в консоль Google Cloud для нового
адреса.

## 13. Риски

- **Сервер.** На портале 4 vCPU / 8 ГБ, у них — отдельный VPS. Сборщики почти
  только ждут сеть, но FitBase ночью и VK раз в час — это постоянная фоновая
  нагрузка. Замеряем после этапов 3 и 5. При нужде — задачи во второй
  контейнер или +4 ГБ памяти.
- **Telegram** из России — только через их шлюз Cloudflare (в России работает
  с перебоями, RU_SELECTEL.md). Сейчас уведомления партнёрам не отправляются.
- **FitBase**: сессия для оснований держится, пока её не отзовут, а вход —
  только вручную через CAPTCHA.
- **VK API**: недокументированные лимиты (лиды ≤ 50, формы ≤ 20). Пагинацию
  проверяем на живых кабинетах.
- **Объём ПДн** (оценки с именами, заявки ЛФ и квиза, переписка): хранение в
  России, узкий доступ, журнал.
- **Неполные выгрузки 1С** 2023–2024: без переформирования «новые / повторные»
  после этих лет считаются неточно — и у них, и у нас.
